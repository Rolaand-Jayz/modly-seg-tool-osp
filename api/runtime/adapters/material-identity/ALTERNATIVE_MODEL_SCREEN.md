# Ticket 07 alternative checkpoint screen

Status: the existing SigLIP2 candidate has one bounded synthetic CPU load/score preflight. This file additionally records source-only screens of FMMC, MatSim, and DINOv2; no new candidate weights were downloaded or executed, no held-out data were accessed, and no GPU or real/DMS imagery was used for these screens. The existing CPU smoke does not change the fixed label/coverage/accuracy gates in `SELECTION_AND_GATES.md`, measure material quality, or accept any candidate.

## Does the audited contract require DMS46?

No. The final audited spec requires an independently replaceable `Classify Material Identity` capability and says its POC may use rendered multi-view crops/features plus an open vision-language or embedding model, provided it supports explicit unknown/ambiguous output and is not coupled to the geometry segmenter. Ticket 07 likewise defines an adapter, not a prescribed model. DMS46 is the current screened/selected reference candidate in implementation notes; its name is not a product/spec mandate. A replacement must still meet every unchanged frozen fixture and AMD gate and use the Modly JSON-lines process-extension seam.

### Additional screen: FMMC (CVPR 2026)

The official [FMMC project page](https://fmmc-project.github.io/) reports material classification accuracy of 0.89 on FMD, 0.64 on DMS-test, and 0.92 on Google-test. These are accuracy results on separate benchmarks, not macro-F1/recall/coverage results on Modly's frozen object-disjoint fixture; they do not establish unknown/ambiguous abstention or target AMD operation. The official [FMMC code repository](https://github.com/fmmc-project/foundation-models-material-classification) contains an MIT code license and instructions to retrieve trained log directories/checkpoints and datasets from Google Drive. The visible source page does not provide immutable checkpoint file identities, checkpoint-specific licensing, or checksums. Its described training pipeline also uses Stable Diffusion 2.1 generated data and DMS training data; reuse rights for those model/data inputs and resulting checkpoints are not resolved by the repository's MIT code license. Therefore FMMC is a research lead, not a currently license-cleared candidate to download/load. Do not stage or execute its checkpoint until the exact checkpoint bytes, checkpoint terms, data/model provenance terms, taxonomy coverage, and dependency/runtime tuple are independently verified. If those gates clear, it would still need development-only screening before any heldout scoring and all unchanged Ticket 07 gates.

### Additional screen: MatSim one-shot material embedding

The author-linked [MatSim implementation](https://github.com/sagieppel/Contrastive-learning-for-one-shot-materials-and-textures-similarity-recognition-from-images) is a closer architectural match to topology-bound region crops than a generic image classifier: it accepts an RGB crop plus ROI mask and emits a 512-value descriptor, intended to find same/similar materials from one or a few labeled exemplars. The author-referenced [Zenodo record](https://zenodo.org/records/7390166) is immutable (DOI `10.5281/zenodo.7390166`) and lists `Net_Code_And_Trained_Model.zip` (472.2 MB, publisher MD5 `a76ba47159cf4fb96e881eb06dd36201`). However, Zenodo's Rights/License field is blank, the linked Git repository's MIT `LICENCE` is for the software and does not explicitly grant rights to trained weights or training data, and no SHA-256 or individual checkpoint digest is published. The model therefore does **not** meet the current license-clear/checkpoint-pin gate. The README reports training with Torch 1.12.1 + CUDA 11.3 on RTX 3090 and requires Torch/OpenCV; no AMD ROCm/MIGraphX execution evidence is published. This is descriptor retrieval rather than a taxonomy classifier: a separate, development-only calibrated mapping from exemplars to the five fixed classes, plus unknown/ambiguous thresholds, would be required. That approach is plausible to screen only after weight/data terms and byte identity are resolved; published material similarity evidence does not establish the frozen classification gates.

### Additional screen: DINOv2 base as a licensed feature encoder

Meta's [official DINOv2 repository](https://github.com/facebookresearch/dinov2) and [official model card](https://github.com/facebookresearch/dinov2/blob/main/MODEL_CARD.md) state that standard DINOv2 weights are Apache-2.0. However, the pinned Hugging Face `facebook/dinov2-base` snapshot at [`f2604a616e0cd01e27e0f1e99be10aea2360524e`](https://huggingface.co/facebook/dinov2-base/tree/f2604a616e0cd01e27e0f1e99be10aea2360524e) contains `README.md` frontmatter declaring CC-BY-NC-4.0, and the HF history shows staff changed that card declaration from Apache-2.0 to CC-BY-NC-4.0 in commit [`960b4558eafd6dfafd3501cac821e0d3adc97982`](https://huggingface.co/facebook/dinov2-base/commit/960b4558eafd6dfafd3501cac821e0d3adc97982). The current Hugging Face model page badge says Apache-2.0, so the staged mirror has conflicting file-level metadata. Until the exact staged safetensors are tied to Meta's Apache-licensed checkpoint or the discrepancy is clarified, this snapshot is **not treated as a license-cleared candidate**; see [`DINOV2_LICENSE_PROVENANCE_REVIEW_2026-09-25.md`](evidence/DINOV2_LICENSE_PROVENANCE_REVIEW_2026-09-25.md). This is only a general visual encoder, with no material names, fixed taxonomy, or unknown/ambiguous behavior. FMMC reports that DINOv2 with a material-trained head can reach `0.79 mIoU / 0.88 mAcc` in its benchmark, but that result belongs to the trained FMMC head and its dataset, not to the bare DINOv2 checkpoint. No license-cleared, pinned material head was identified here. An exemplar or linear-probe classifier over topology-bound DINOv2 region features could be explored using a properly separated development-only fitting/calibration procedure after provenance is resolved. This is a **research route**, not an acceptance-ready classifier or evidence that the small existing development fixture can train a generalizable head.

## Recommendation and remaining blockers

The spec permits replacing DMS46. Google SigLIP 2 base patch16 224 is the only candidate found here with an explicit permissive checkpoint license, a pinned immutable checkpoint file and publisher SHA-256, open-vocabulary label prompts, and a plausible batch-one 16 GiB path without an identified NVIDIA-only custom op. Treat that as a **probe candidate only**, not a result. Before replacement or acceptance, Modly must run the candidate through the existing process-extension boundary using actual material-region crops and source evidence, then score the unchanged object-disjoint held-out set against every frozen class, abstention, coverage, ROCm/MIGraphX parity/latency, and VRAM threshold. The held-out fixture currently lacks actual verified imagery/maps and distinct object-instance annotations, so quality comparison cannot yet run. Keep criterion 1 unchecked until those measurements exist.

### Expected Modly region binding changes before a real probe

The current DMS46 path returns dense image class IDs and aggregates pixels through calibrated face maps. SigLIP2 emits image/text similarity for an image or crop, not a dense material-ID image. A viable replacement must therefore extend the existing classifier adapter/process-extension input to expose, for each current topology-bound material-region ID:

1. The source observation ID/digest, camera/projection identity, face-to-pixel map digest, and material-region ID plus topology revision.
2. A deterministic masked crop for the region and each view where it is visible. Pixels outside that region must be removed or neutralized before model preprocessing; regions must not be merged across IDs or inferred from part/material slots.
3. A fixed prompt/label vocabulary, prompt-template revision, exact processor/tokenizer/config identities, and per-view raw similarity outputs. Similarity is not a calibrated probability; confidence must be represented as uncalibrated evidence until calibration passes.
4. A frozen, validation-only threshold/margin policy mapping low-evidence crops to `unknown` and competing near-ties/inconsistent views to `ambiguous`; held-out examples cannot be used to tune it.
5. Cross-view aggregation scoped to the same topology-bound region, with observations, crop/input digests, winning/competing text candidates, threshold decision, checkpoint/runtime provenance, and topology invalidation carried into the assertion/stage artifact.

Those changes must preserve the current process-extension seam and keep identity separate from part semantics and PBR. No output mapper accepting caller predictions can substitute for the model invocation.
